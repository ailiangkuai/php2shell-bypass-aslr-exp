# CVE-2026-109619 在 PHP 5.6.40 FPM 的窗口1排除证据

日期：2026-10-23 | 环境：[docker56](../docker56/)（php:5.6.40-fpm + nginx 1.27，memory_limit=8M，单 worker `pm.max_requests=0`） | 探针：[tools56/probe5_56.py](../tools56/probe5_56.py)

## 结论

CVE-2026-109619（GHSA-6wmf-4rv5-p3rp）的利用模型要求：producer 请求在 **RINIT 之前**（multipart 解析期）把 session 全局状态发布到 worker 进程，随后 OOM bailout 早退留下半初始化状态，consumer 请求在同一 worker 内 pre-RINIT 消费残留。5.6.40 实测：**A 请求（producer）必致 FPM child exit(70) + master 重拉全新 child，跨请求残留结构性不存在**。至此三个窗口全部实测闭合（窗口2/3 见 [docker56/README.md](../docker56/README.md) 的 probe3 记录），与上游不给 5.6 补丁互恰。

## 三窗口排除总表

| 窗口 | producer OOM 位置 | worker 命运 | 残留状态 | 探针 |
|---|---|---|---|---|
| 1. startup/multipart 解析期（pre-RINIT） | `rfc1867` 逐 5KB erealloc 累积 12MB 字段 → memory_limit | **child exit(70)**，master 重拉 | 进程销毁，无残留 | probe5_56.py（本文档） |
| 2. 执行阶段 fatal | `php_execute_script` 内 `str_repeat` OOM | 存活 | RSHUTDOWN 完整跑完，无差异（3 轮 NORMAL） | probe3_56.py 变体 A |
| 3. RSHUTDOWN 内 OOM | `ps_write` 序列化 OOM | 存活 | `zend_try` 吞 bailout 后仍执行 `php_rshutdown_session_globals`（session.c L2414-2417），PS(id)/PS(http_session_vars) 正常置空 | probe3_56.py 变体 B |

## 窗口1源码链（为什么 5.6 startup 期 OOM 必杀 worker）

完整 bailout 逃逸路径（php-5.6.40 源码，容器内 `docker-php-source extract` 后 `/usr/src/php/`）：

```c
// main/rfc1867.c L660 multipart_buffer_read_body —— OOM 触发点
buffer->inputpos += buflen;  // erealloc 逐 5KB 累积整字段，12MB 字段 vs memory_limit=8M 必触发

// main/php_variables.c L711 php_hash_environment —— 无独立 try 包裹
PHPAPI int php_hash_environment(TSRMLS_D)
{
    ...
    zend_activate_auto_globals(TSRMLS_C);  // _POST auto global → sapi_module.treat_data(PARSE_POST) → rfc1867 multipart 解析
}

// main/main.c L1616 php_request_startup（FPM 用非 APACHE_HOOKS 路径）—— zend_try 捕获点
zend_try {
    ...
    php_hash_environment(TSRMLS_C);   // L1685：multipart OOM bailout 在此被捕获
    zend_activate_modules(TSRMLS_C);  // （RINIT 尚未开始 → 8.4 补丁要防的 "pre-RINIT 残留" 阶段）
} zend_catch {
    retval = FAILURE;                 // 转化为返回值，进程不立即死
}

// sapi/fpm/fpm/fpm_main.c —— FAILURE → 必杀 worker 的两条路径
zend_first_try {                                      // L1915 包整个请求循环
    while (fcgi_accept_request(&request) >= 0) {
        if (php_request_startup(TSRMLS_C) == FAILURE) {   // L1927
            ...
            return FPM_EXIT_SOFTWARE;                 // 路径1：exit(70)
        }
        ...
        php_request_shutdown((void *) 0);             // L2021 正常路径
    }
} zend_catch {                                        // L2045
    exit_status = FPM_EXIT_SOFTWARE;                  // 路径2：逃到外层 catch 同样 exit(70)
}
```

关键点：`php_request_startup` 的 `zend_try` 把 OOM bailout 降级为 `FAILURE` 返回值，进程本身不死——但 fpm_main.c 对 startup FAILURE 的处理是退出整个 child（L1927-L1935）。即使 bailout 逃过内层 try（如 zend_activate_modules 内），外层 `zend_first_try`/`zend_catch`（L1915/L2045-2046）仍是第二道 exit(70)。**child 一死，request 内存（含已发布的 PS(id)/PS(http_session_vars) 残留）随 `php_module_shutdown` + 进程销毁整体消失，master 重拉的全新 child 从 MINIT 级全局开始，无任何跨请求状态**。

对照 8.4 修复（8.4.27 给 MULTIPART_EVENT_START 加 `php_rinit_session_globals()` + `PS(in_r1867_update)` 标志）：8.4 Apache mod_php worker 在 startup OOM 后存活，残留可被下一请求消费，所以才需要补丁；5.6 FPM 的 worker 直接死，无补丁必要。

## probe5 实测（2026-10-23）

A 请求构造：multipart 字段序 = `PHPSESSID`（受害 SID）→ `PHP_SESSION_UPLOAD_PROGRESS` → 文件字段 f（触发 FILE_START → `php_rinit_session(0)` + `PS(id)=estrndup`，即 109619 的"pre-RINIT 发布"）→ 12MB big 字段（erealloc 累积触发 OOM）。B 请求：同 SID + progress + 文件字段（END 事件 cleanup 消费残留）。C 请求：GET /index.php 存活探测。

观测结果：

| 请求 | 响应 | 实际语义 |
|---|---|---|
| A（producer） | 200 + chunked + 空 body（`0\r\n\r\n`），或手动重发得 502 Bad Gateway | worker exit(70)；nginx 视死亡时序返回已收到的部分或 502，两种形态同义 |
| B（consumer） | 200 正常 | 全新 child，无残留可消费 |
| C（存活探测） | 200 OK | master 已重拉，服务恢复 |

### 探针判定逻辑说明

probe5_56.py 的 `a_fatal` 判定（查响应中 "Allowed memory size" fatal 文本）在本环境**必然为 False 且不构成否定证据**：worker 在 fatal 输出送达 nginx 之前已 exit(70)，故 A 的响应要么是 200 空 chunked、要么是 502——两者都伴随 `child NNN exited with code 70` 日志。**窗口1的 OOM 确证应以 FPM 日志的 exit(70) + 重拉记录为准**（上表已给出 4 次独立复现），而非响应文本。
